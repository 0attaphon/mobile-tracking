# BUDDY RISE — เควสนอกบ้าน เหรียญแลกรางวัล และราคาสินค้า

วันที่: 2026-09-22
สถานะ: แบบในบทสนทนาได้รับอนุมัติแล้ว เอกสารนี้รอผู้ใช้ตรวจทานก่อนเขียนแผนลงมือ

## 1. เป้าหมายและขอบเขต

ใช้เหรียญเดิมร่วมกันระหว่างร้านค้าในเกมและการแลกของจริง เพิ่มเควสนอกบ้าน 10 รายการแบบถ่ายภาพตรวจบนเครื่อง และให้แอดมินกรอกรหัสนักเรียนกับจำนวนเหรียญที่หักในเว็บเดิม

ปรับราคาสินค้าปัจจุบันรวมเป็น 12,000 เหรียญ ตั้งเป้าผู้เล่นใหม่รายได้เฉลี่ย 150–180 เหรียญต่อวันสะสมครบประมาณ 2–3 เดือน ผู้เล่นมากกว่านี้สะสมเร็วกว่าได้ ตัวเลขไม่รวมการใช้เหรียญแลกของจริงหรือสินค้าที่เพิ่มในอนาคต

ขอบเขตประกอบด้วยเควสและการตรวจภาพ กระเป๋าเหรียญที่รองรับการหักจากเว็บ ราคาสินค้า และแก้โบนัส streak ที่จ่ายซ้ำในวันเดียว ทั้งหมดใช้กระเป๋าเดียวกันและต้องทดสอบร่วมกัน ไม่เพิ่มแค็ตตาล็อกของรางวัลจริง ระบบสต็อก หรือแต้มชนิดใหม่

## 2. หลักฐานจากระบบปัจจุบัน

- `pet-focus/src/types/shop.ts`: สินค้าที่ไม่ถูกคอมเมนต์ 69 รายการ ได้แก่เครื่องแต่งกาย 38 พื้นหลัง 29 และสัตว์ 2 รวม 19,840 เหรียญ ณ working tree ที่ตรวจ
- `types/focus.ts`: โฟกัส 60 นาทีได้ 40 เหรียญ และ 120 นาทีได้ 100 เหรียญ เควสเดิมมีรางวัลหลายระดับ ไม่ได้มีเพียง 4 เควสตามคู่มือเก่า
- `choreQuestStore.ts`: เลือกเควสงานบ้าน 3–5 รายการด้วย seed นักเรียนและวัน บันทึกความสำเร็จและ hash รูปบนเครื่อง
- `choreVerifier.ts`: ตรวจใบหน้าและ image labels ยังไม่มีการตรวจโครงร่างหรือท่าทาง
- `petStore.ts` และ `services/supabase/sync.ts`: ปรับยอดบนเครื่องแล้วส่ง delta พร้อมคิวออฟไลน์ ไม่มีรหัสรายการกันประมวลผลซ้ำ และไม่ได้ใช้ยอดที่ RPC ส่งคืน
- RPC เดิมใช้ `greatest(0, coins + delta)` จึงไม่เพียงพอต่อการปฏิเสธซื้อเมื่อยอดไม่พอ
- `focusStore.ts`: เลือกโบนัสจาก currentStreak แม้โฟกัสรอบถัดไปในวันเดียว จึงอาจรับโบนัสวัน milestone ซ้ำ
- Admin มีการตรวจสิทธิ์ผ่าน `requireAdmin` และฐานข้อมูลมี `is_admin()` อยู่แล้ว

คู่มือและไฟล์หลายรายการมีการแก้ค้างอยู่ก่อนงานนี้ ต้องคงงานเหล่านั้นไว้ สเปกนี้อิงแค็ตตาล็อกใน working tree ไม่ใช่ HEAD

### ตารางหมุน

- เพิ่มหมวดนอกบ้านในหน้าเควสเดิม งานบ้านยังทำได้ตามระบบเดิม
- แสดงนอกบ้านวันละ 4 เควส รับเหรียญไม่เกิน 3 เควส วันหนึ่งเควสเดียวรับได้ครั้งเดียว
- ใช้วัน Asia/Bangkok และรหัสนักเรียนเป็นฐาน ชุดเดิมคงอยู่หลังปิดเปิดแอปหรือซิงก์ใหม่
- ใช้รอบ 3 วัน: สับลำดับคลัง 10 รายการแบบทำซ้ำได้ แล้วจัด 4/4/2 รายการ รายการอีก 2 ของวันที่สามเลือกจากวันแรก จึงเห็นครบ 10 ในสามวันโดยไม่นับการเปลี่ยนเอง
- จัดลำดับแบบมีข้อจำกัดให้แต่ละวันมีอย่างน้อยกิจกรรมเคลื่อนไหวหนึ่งรายการและกิจกรรมดูแลพื้นที่หรือธรรมชาติหนึ่งรายการ เลี่ยงซ้ำวันติดกันรวมรอยต่อรอบเท่าที่ทำได้ หากข้อจำกัดชนกัน ให้ความครบ 10 รายการและความหลากหลายมาก่อนการไม่ซ้ำ
- เปลี่ยนได้ 1 เควสที่ยังไม่สำเร็จต่อวัน เลือกตัวแทนที่ไม่อยู่ในชุดวันนี้และยังไม่ทำวันนี้ บันทึกการเปลี่ยนไม่ให้รีเซ็ตสิทธิ์ด้วยการเปิดแอปใหม่ เควสที่เปลี่ยนออกส่งรับเหรียญไม่ได้
- โควตา 3 เควสนอกบ้านไม่ใช่โควตางานบ้านรวม ตัวเลข 3–4 เควสต่อวันในแบบเศรษฐกิจหมายถึงจำนวนที่ผู้เล่นเลือกทำจากทั้งสองหมวด

### การตรวจภาพ

ถ่ายผ่านกล้องในแอป → ตรวจใบหน้า → ตรวจรูปซ้ำข้ามเควส → ตรวจบริบทและท่าทางตามชนิด → บันทึกผลและให้เหรียญหนึ่งครั้ง หากไม่ผ่านแจ้งคำแนะนำที่ตรงเหตุผลและลองใหม่ได้โดยไม่หักเหรียญ

แยกการเลือกเควส การตรวจภาพ และการรับรางวัลออกจากกัน ตัวตรวจคืนผลผ่าน/ไม่ผ่าน เหตุผล และหลักฐานที่พบ ไม่แก้ยอดเหรียญเอง

เควสทั่วไปใช้ตัวตรวจใบหน้าเดิมร่วมกับ labels ที่ทดสอบแล้ว สองเควสท่าทางต้องมีตัวตรวจ landmark บนเครื่องและเงื่อนไขข้อต่อเฉพาะท่า ห้ามใช้เพียง label คนหรือกลางแจ้งแทนการตรวจท่า รูปที่ไม่เห็นข้อต่อสำคัญให้ขอถ่ายใหม่

ไม่อัปโหลดภาพหรือข้อมูลใบหน้าไปเซิร์ฟเวอร์ ส่งเฉพาะข้อมูลการรับรางวัลและ fingerprint สำหรับกันส่งภาพเดิม คง fingerprint หลังลบภาพชั่วคราว ไม่อ้างว่าการเทียบ hash ป้องกันภาพที่ถูกดัดแปลงได้ทั้งหมด

ก่อนเปิดใช้แต่ละเควส ทดสอบบน Android dev client ด้วยภาพที่ได้รับอนุญาตอย่างน้อย 20 ภาพตรงเงื่อนไขและ 20 ภาพไม่ตรง แยกภาพปรับเกณฑ์ออกจากภาพประเมิน เป้าหมายผ่านภาพถูกอย่างน้อย 85% และรับภาพผิดไม่เกิน 10% รวมภาพบริบทเหมือนกันแต่กิจกรรมผิด หากไม่ผ่านให้ปรับตัวตรวจและทดสอบใหม่ ไม่เปิดโดยลดเกณฑ์จนเหลือการตรวจคนอย่างเดียว

การเลือกไลบรารีหรือโมเดลตรวจท่าต้องตรวจความเข้ากันได้กับ Expo SDK 52 / RN 0.76 ที่ติดตั้งจริงก่อนเขียนแผน native integration เอกสาร AGENTS อ้าง SDK 56 แต่ package.json ยังเป็น SDK 52 งานนี้ไม่อนุมัติให้อัปเกรด Expo โดยอัตโนมัติ

## 4. เว็บแอดมินและยอดเหรียญ

หน้าใหม่ในเว็บที่ต้องล็อกอิน: กรอกรหัสนักเรียน → ค้นหาแบบตรงรหัส → แสดงรหัส ชื่อเล่น/ห้องที่มี และยอดยืนยันล่าสุด → กรอกจำนวนเต็มบวก → แสดงยอดก่อน/หลัง → ยืนยัน ไม่บังคับกรอกชื่อของรางวัล

ห้ามศูนย์ จำนวนลบ ทศนิยม ค่าที่เกินขอบเขต integer หรือเกินยอด หากไม่พบรหัสให้แจ้งชัดและไม่แสดงฟอร์มหัก ปุ่มปิดระหว่างส่ง หากยอดเปลี่ยนจากหน้าสรุปให้โหลดใหม่และให้ผู้ใช้ยืนยันสรุปล่าสุด

เซิร์ฟเวอร์ตรวจ `is_admin()` ทุกครั้ง ใช้ transaction เดียวล็อกกระเป๋านักเรียน ตรวจยอดและ version หักเหรียญ และบันทึกผู้ทำรายการ นักเรียน จำนวน ยอดก่อน/หลัง เวลา และ request ID การส่งซ้ำด้วย ID เดิมคืนผลเดิมโดยไม่หักเพิ่ม ถ้า ID เดิมมากับข้อมูลคนละชุดให้ปฏิเสธ

แอดมินดูประวัติของเด็กได้ เด็กเห็นประวัติเหรียญของตัวเองในแอป ข้อมูล audit แก้หรือลบผ่าน client ไม่ได้ รุ่นแรกไม่มีหน้าจอย้อนรายการหรือเพิ่มแต้มทั่วไป ไม่เพิ่มฟอร์มของรางวัลหรือสต็อก

### กระเป๋ากลางและการซื้อ

- ยอดยืนยันใน Supabase เป็นยอดที่ใช้ซื้อหรือหักจริง ทุกการเปลี่ยนยอดผ่านบริการกระเป๋าเดียวกัน
- เก็บ ledger พร้อม request ID, student, type, delta, balance before/after, actor, source และเวลา ใช้ยอด version ป้องกันคำตอบเก่าทับยอดใหม่
- ซื้อสินค้าด้วย item ID ให้เซิร์ฟเวอร์อ่านราคาจากแค็ตตาล็อกที่มี version ตรวจยอดและ ownership แล้วหักพร้อมบันทึกสิทธิ์เป็นเจ้าของใน transaction เดียว การ retry หลังแอปปิดต้องคืนสินค้าเดิมโดยไม่คิดเงินซ้ำ
- โฟกัสและเควสยังทำออฟไลน์ได้ รางวัลเก็บเป็นรายการรอส่งด้วย ID คงที่ แสดงยอดยืนยันกับรางวัลรอซิงก์แยกกัน รางวัลรอซิงก์ยังใช้ซื้อหรือให้ครูหักไม่ได้
- ต้องออนไลน์เพื่อซื้อสินค้าใหม่และหักโดยแอดมิน ของที่มีแล้วสวมและใช้งานออฟไลน์ได้
- คิวต้องเขียนและ flush แบบไม่ทำรายการหายเมื่อมีการเพิ่มพร้อมกัน ผูกกับนักเรียนเจ้าของคิว และใช้ ID เดิมตลอดการ retry
- เมื่อออนไลน์หรือกลับเข้าแอป ให้ส่งคิวและอ่านยอด/ประวัติใหม่ เมื่อเปิดหน้าร้านให้อ่านยอดล่าสุดด้วย ไม่รับประกันว่าเด็กที่ออฟไลน์จะเห็นยอดหักทันที
- การรับรางวัลตรวจเจ้าของรายการ ค่าเหรียญจากกฎเซิร์ฟเวอร์ เควสที่ถูกเลือก วัน และโควตา ไม่เชื่อค่า delta อิสระจาก client การตรวจภาพยังอยู่บนเครื่อง จึงไม่อ้างว่าป้องกันแอปดัดแปลงได้สมบูรณ์

## 5. ราคาและโบนัส

ราคาสินค้าในภาคผนวกรวม 12,000 เหรียญ ปรับตามสัดส่วนราคาเดิมแล้วปัดเป็นขั้นละ 5 ด้วย largest remainder ให้ยอดรวมตรงเป้า รักษาลำดับราคาเดิมและของเริ่มต้นราคาถูก ไม่มีการริบของเดิม หักเหรียญย้อนหลัง หรือคืนส่วนต่างจากการลดราคา

คงอัตราโฟกัสและเควสงานบ้านเดิม เพิ่มเฉพาะรางวัลนอกบ้านตามตาราง แก้ streak ให้จ่ายโบนัส milestone ครั้งเดียวในวันนั้น และให้กฎเดียวกันบังคับที่จุดรับรางวัลเซิร์ฟเวอร์ การ retry session ไม่เพิ่มเหรียญซ้ำ ไม่เพิ่มโควตาโฟกัสใหม่

| สมมติฐาน | รายได้ฐาน/วัน | วันสะสม 12,000 รวมโบนัส 840 |
|---|---:|---:|
| 60 นาทีครั้งเดียว + 3 เควส เฉลี่ย 25 | 115 | 98 |
| ผู้เล่นระดับกลาง | 150 | 75 |
| ผู้เล่นระดับกลาง | 180 | 62 |
| 120 นาทีครั้งเดียว + 4 เควส เฉลี่ย 25 | 200 | 56 |

สูตร `ceil((12000 - 840) / รายได้ฐานต่อวัน)` ใช้เฉพาะตัวอย่างที่โฟกัสต่อเนื่องเกิน 30 วัน โบนัสวันที่ 1,3,7,14,30 รวม 840 ไม่มีโบนัสทุก 30 วันอัตโนมัติ ผู้เล่นที่ขาดวัน เลือกเควสราคาต่างกัน หรือแบ่งโฟกัสหลาย session มีผลลัพธ์ต่างกัน การแลกของจริงทำให้เก็บครบช้าลง ไม่มีการรับประกันวันครบรายบุคคล

แยกหน่วย: outdoor catalog/scheduler, photo/pose verifier, reward service, wallet/ledger, admin deduction UI และ versioned shop catalog ใช้ Supabase RPC เป็นจุดร่วมด้านยอดและสิทธิ์ ไม่ให้เว็บเขียนยอดโดยตรง

พื้นที่งานหลัก: `pet-focus/src/types`, `stores/choreQuestStore.ts`, `services/choreVerifier.ts`, `services/supabase/sync.ts`, `stores/petStore.ts`, `stores/focusStore.ts`, หน้าเควส/ร้านค้า/ประวัติ, `admin-web/src/app`, และ migration ใน `supabase/migrations` อัปเดต `docs/USER_GUIDE.md` กับ `pet-focus/AGENTS.md` ตามพฤติกรรมจริงเมื่อ implement

ย้ายแบบ versioned และเพิ่มตารางก่อนเปิดใช้: ยอดเริ่มต้นใช้ coins ที่เซิร์ฟเวอร์มีอยู่ ให้ client รุ่นเปลี่ยนผ่าน flush คิวเดิมก่อนเปิดกระเป๋าใหม่และนำเข้า ownedItems ที่รู้จักเพียงครั้งเดียวเพื่อรักษาของเดิม บันทึกการนำเข้าต่อเด็ก ปฏิเสธ item ID นอกแค็ตตาล็อก การนำเข้าจากเครื่องเก่าเป็นข้อยกเว้นความน่าเชื่อถือเฉพาะการย้าย

คิว delta เดิมไม่มี ID จึงพิสูจน์ย้อนหลังไม่ได้ว่ารายการใดเคยส่งสำเร็จแต่ไม่ได้รับคำตอบ ห้ามเดาหรือ replay อัตโนมัติในเส้นทางใหม่ เก็บคิวเก่าไว้และแสดงสถานะซิงก์ไม่พร้อมจนเคลียร์ด้วยเส้นทางเปลี่ยนผ่าน ทดสอบกรณีนี้และรายงานข้อจำกัดก่อน rollout

ก่อนเปิดการหักโดยแอดมินต้องตัดเส้นทางเขียนยอดอิสระของ client เก่า รวม RPC และ RLS ที่เกี่ยวข้อง ให้รุ่นเก่าแจ้งให้อัปเดตสำหรับการใช้เหรียญ การ rollback ปิดฟีเจอร์ใหม่และคง ledger/ยอดไว้ ไม่ย้อนกลับไปเปิดการหักแบบไม่มีการตรวจยอด ทั้งการ deploy และการแก้ข้อมูล production ไม่อยู่ในขั้นเขียนสเปก

## 7. การทดสอบและเกณฑ์เสร็จ

- ตารางหมุน: วันละ 4 ครบคลังในรอบ 3 วัน หมวดหลากหลาย restart คงเดิม เปลี่ยนครั้งเดียว รับนอกบ้านได้ 3 ครั้ง และข้ามวันไทยถูกต้อง
- เควส: เควสที่ไม่ได้รับเลือก/ถูกเปลี่ยนออก/รับแล้วรับอีกไม่ได้ รูปซ้ำข้ามเควสถูกปฏิเสธ ออฟไลน์แล้ว retry ไม่เพิ่มรางวัลซ้ำ
- ภาพ: ประเมินแต่ละเควสตามชุดภาพในหัวข้อ 3 พร้อมตรวจใบหน้าผิด ภาพไม่เห็นข้อต่อ และท่าผิด เก็บรายงานอัตราผ่านจริง
- กระเป๋า: นักเรียนเรียกหักแบบแอดมินไม่ได้ สองแอดมินหักพร้อมกันและซื้อพร้อมหักแล้วไม่ติดลบ คำตอบหายแล้วส่งซ้ำให้ผลเดิม ความล้มเหลวกลาง transaction ไม่ทิ้งยอดหรือ ownership ครึ่งเดียว
- ซิงก์: คิวเพิ่มระหว่าง flush ไม่หาย คำตอบเก่าไม่ทับใหม่ นักเรียนคนละคนไม่ใช้คิวกัน และแสดงยอดหักหลัง reconnect
- ราคา: 69 ID ตรงแค็ตตาล็อก ยอดรวม 12,000 ราคาฝั่งแอปตรงเซิร์ฟเวอร์ ของเดิมยังอยู่ และตัวอย่างวันสะสมคำนวณตรง
- Streak: รอบที่สองของวัน milestone ไม่มีโบนัสเพิ่ม วันใหม่และ catch-up/freeze เดิมยังทำงาน
- ย้ายระบบ: ทดสอบผู้ใช้ใหม่ ผู้ใช้มีของเดิม มีคิวออฟไลน์ ติดตั้งใหม่ และ client เก่าไม่สามารถข้ามกฎกระเป๋าใหม่
- รัน typecheck/build ที่เกี่ยวข้องและ smoke test บน Android dev client จริง รวมเว็บค้นหารหัส หัก และดูประวัติ ไม่ถือว่าผ่านงาน native จาก TypeScript อย่างเดียว

## 8. ลำดับส่งมอบ

หลังผู้ใช้ตรวจเอกสารนี้ ให้ใช้ writing-plans วางแผนตาม dependency: ตรวจความเป็นไปได้ตัวตรวจภาพและท่า → กระเป๋า/การย้าย/กฎรางวัล → เว็บหักและการซื้อออนไลน์ → เควสหมุนและ UI → ราคา/โบนัส → ทดสอบร่วมและอัปเดตคู่มือ ตัวตรวจที่ยังไม่ผ่านเกณฑ์เป็นตัวขวางการเปิดใช้เควสนั้น ไม่แทนที่ด้วยการให้ผ่านจาก label ทั่วไปโดยเงียบ ๆ
